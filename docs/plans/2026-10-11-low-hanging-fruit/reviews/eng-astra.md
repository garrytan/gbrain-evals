The plan needs changes before implementation. ### F1 — High: The live expansion arm can silently become the no-expansion control

Item 1b says every `query` makes an expansion call and gates removal on the paired recall difference. The implementation does not guarantee a call: `gbrain/src/core/search/expansion.ts:57-65` skips short queries and unavailable providers, and `:82-83` catches every expansion exception and returns only the original query. Consequently, the catch in `gbrain/src/core/search/hybrid/arms.ts:232-247` never sees those failures; it can report `expansion_applied: false` without an `expansion_failed` degradation. An unavailable or failing expansion provider could make both paid arms effectively identical and pass non-inferiority. Reporting aggregate model-call counts does not make that a valid experiment.

Add an explicit treatment-validity gate before spending: retain per-question expansion eligibility, attempted provider calls, provider outcomes, returned variants, and fallback reasons. Distinguish a legitimate short-query skip or successful original-only response from a swallowed provider failure. Reject an unavailable provider, budget refusal, or failed treatment as an invalid/incomplete run, not evidence that expansion is unnecessary. Apply equivalent validity checks to embeddings and reranking. Keyless forced probes must show that a throwing expansion transport cannot produce a shippable paired verdict. Use the actual selected runner's paid-request guard; the guard installed by `gbrain-evals/eval/runner/longmemeval.ts:1165-1178` is not installed simply by calling `gbrain/src/commands/eval-longmemeval.ts`.

### F2 — High: The default-mode gate leaves the changed `query` path uncontrolled

The four arms compare modes only through `search`, while both `query` arms use `balanced`. But `search` fixes its default limit at 20 (`gbrain/src/core/ops/search.ts:689-692`), and `query` deliberately inherits mode-dependent limits (`:817-833`, `:975-985`). The requested limit also changes the candidate-pool request (`gbrain/src/core/search/hybrid/request.ts:167-169`), and `query` adds its own arms and confidence escalation (`gbrain/src/core/ops/search.ts:1030-1068`). A clean `search` comparison cannot establish non-inferiority for the default `query` transition from tokenmax to balanced. The fresh-init receipt test checks configuration and calls, not recall on that transition.

Add a tokenmax-via-`query` arm, holding expansion constant against the corresponding balanced arm, and gate the default flip on both operation paths. Distinguish the scoring cutoff of five from the operation's requested limit: inheriting the old harness's `limit: topK` (`gbrain/src/commands/eval-longmemeval.ts:1426-1437`) would bypass the very default being changed. Freeze the caller context and actual request arguments, score the returned first five, and verify the resolved server mode rather than relying on a remote per-call mode override. Keep this inside the approved cap; if it does not fit, defer the general default flip rather than claim the search-only result covers it.

### F3 — High: Additive stage timings are incompatible with overlapping work and retries

Item 5 requires named durations plus `other` to equal operation wall time. Keyword counting intentionally overlaps the hybrid call (`gbrain/src/core/search/keyword-paging.ts:118-128`; `gbrain/src/core/ops/search.ts:759-777`). Lexical arms run concurrently (`gbrain/src/core/search/hybrid/arms.ts:70-96`), as do variant embedding and vector batches (`:403-406`). Summing ordinary stage elapsed times double-counts overlap; computing `other = total - sum` can produce a negative duration. Serializing the work to make the equation true would introduce the latency regression this item is supposed to diagnose.

Use a monotonic per-operation timing collector and publish independent wall time plus explicitly non-additive stage durations, or specify an exclusive-time attribution policy before implementation. Accumulate every attempt, including a discarded CRAG rerun and the low-to-high retry: the current code replaces captured metadata when an escalation wins (`gbrain/src/core/ops/search.ts:1110-1118`) and only emits the inner retry's metadata (`gbrain/src/core/search/hybrid.ts:1163-1167`). Finalize after evidence/response assembly, not at today's pre-assembly capture point (`gbrain/src/core/ops/search.ts:788-794`). Gate with overlapping delayed stubs, a losing escalation, a detail retry, an early empty return, and a throwing stage. Assert nonnegative, finite values and unchanged scheduling, not the proposed invalid sum.

### F4 — Medium: Retrieval metadata is discarded before Cat 40 writes its receipts

Adding timings to `_meta.retrieval` and GBrain's eval capture does not make Cat 40 retain them. `gbrain-evals/eval/runner/cat40/gbrain-arm.ts:140-148` reduces the MCP response to concatenated text content and drops `_meta`. The arm interface returns only a string (`gbrain-evals/eval/runner/cat40/loop.ts:23-34`), and its persisted tool event contains text, characters, and outer wall time but no metadata (`:44`, `:186-197`). Item 5's stated receipt consumer therefore remains disconnected.

Include an explicit metadata side channel in the Cat 40 adapter and receipt schema, keyed to the individual tool call rather than a mutable last-result slot. Keep diagnostic timing metadata out of model-visible text so instrumentation does not inflate the tool payload being optimized. A scripted, keyless Cat 40 test should return known MCP timings, persist them in the receipt, and prove the model input string and character count are unchanged.

### F5 — High, urgent existing safety issue: Batched exact entity lookup bypasses quarantine

The proposed byte-identical entity optimization would preserve a read-policy hole. Single-name `entity` passes `omitQuarantined: true` for remote callers (`gbrain/src/core/verbs.ts:243-248`), but the batch resolver does not (`gbrain/src/core/verbs/entity-names.ts:49-51`). Exact-title/slug/suffix candidates are read with a private-page predicate, not a quarantine predicate (`gbrain/src/core/verbs/entity-card.ts:246-259`), and quarantine filtering is conditional on that omitted option (`:305-308`). The batch then retrieves the body and emits its lead (`gbrain/src/core/verbs/entity-names.ts:57-72`). The private predicate does not supply the missing quarantine check (`gbrain/src/core/search/private-visibility.ts:46-49`, `:90-92`), and MCP serialization does not add one (`gbrain/src/core/agent-output.ts:863-869`).

The existing quarantine test only exercises a batch alias, `KTCO`, while the single-name check uses the name (`gbrain/test/entity-names.test.ts:76-81`). That does not cover a remote `names: ["crm/kite-co"]` exact lookup. Quarantine includes instruction-like content, not just junk (`gbrain/src/core/quarantine.ts:65-67`), so this can expose content intentionally withheld from agents. Identity-sibling selection also lacks a quarantine condition (`gbrain/src/core/mentions/siblings.ts:75-88`).

Route this to the read-policy/security owner through the coordinator now. Add an explicit safety exception to item 4's parity requirement, or land a coordinated safety fix first; do not require parity with unsafe output. Add remote exact-slug, exact-title, suffix, alias, runner-up, and sibling fixtures, alongside trusted-local visibility checks. This is established from code; I did not execute a reproduction under the review's write restrictions.

### F6 — Medium: The degradation signature is lost before the notice ledger sees it

Item 3 targets a stage-and-reason signature, but `Notice` has no such field (`gbrain/src/core/agent-output.ts:72-79`). `degradedRecallNotice` receives structured stages, renders them into prose, and drops them from its return value (`gbrain/src/core/interop-notices.ts:136-164`). Some reasons are absent from that prose, and rerank prose includes a changing session count (`:145-149`). Hashing `why` would either miss a changed reason or make every repeat appear new. Changing only the ledger's current `${session}|${code}` key (`gbrain/src/core/notice-ledger.ts:69-84`) cannot implement the specified behavior safely.

Specify a bounded, internal dedupe identity carried from the structured producer to the ledger and deliberately omitted from wire rendering. Canonicalize the sorted, unique stage/reason pairs; do not include query text, counts, provider exception strings, or stage arrival order. Test identical degradation with increasing counts, reversed stage order, a changed reason on the same stage, multiple simultaneous stages, CLI/stdio behavior, and HTTP's unchanged per-call behavior. The two proposed probes do not cover these distinctions.

### F7 — Medium: `auto: false` needs a final-result and first-run-decision contract

The proposed explicit init flag is underspecified at the output boundary. The picker's `auto` value currently exists only in a phase log (`gbrain/src/commands/init-mode-picker.ts:220-227`). Under `init --json`, ordinary stdout goes to stderr and a different document is emitted once (`gbrain/src/commands/init-json.ts:1-9`, `:22-34`). That final result is built from `firstRunBundle`, whose input contains only mode/reason and unconditionally creates an unanswered search-mode decision when present (`gbrain/src/commands/init-first-run.ts:25-27`, `:99-115`). The picker callback also currently fires for the recommendation before the interactive selection (`gbrain/src/commands/init-mode-picker.ts:214-216`, `:278-282`). Simply adding an explicit flag and logging `auto: false` would still let the agent be asked to confirm a choice it already supplied.

Define a typed applied-decision result with mode and provenance, carry it into the final JSON document on both engines and the prefer-Postgres wrapper, and omit only the search-mode ask when the operator's choice was explicit. Define re-init precedence instead of accidentally defeating the existing idempotence guard. Add invalid-value/no-write, explicit-choice/no-reprompt, existing-brain, and final-stdout-only tests; preserve unrelated first-run decisions.

### F8 — Medium: The existing-brain notice misstates what happens to synopsis embeddings

Item 1 promises to warn that per-chunk synopses stop being used when switching to balanced. Existing synopsis text is baked into stored vectors; changing `search.mode` does not select a different stored vector version or rewrite those vectors. Inline imports already demote the synopsis tier to title (`gbrain/src/core/import-contextual-mode.ts:32-37`). Changing an existing page's synopsis vectors requires the contextual service's explicit embedding publication (`gbrain/src/core/contextual-retrieval-service.ts:321-333`). The narrowing transition itself requires no reindex (`gbrain/src/core/search/mode-switch-ux.ts:137-147`).

Describe the immediate read-side changes separately from future write/backfill policy. Say that existing contextual embeddings continue serving until explicitly replaced; do not imply removal of previously embedded context or immediate index conversion. Add a no-provider test that changes only the mode and verifies existing vectors and contextual stamps are untouched. Keep any re-embedding outside this consent-free recommendation.

### F9 — Medium: The non-inferiority rule still lacks a reproducible interval definition

The implementation plan at `eng-implementation.md:73-74` and `:98-101` specifies a lower bound but not its confidence level, sidedness, paired interval method, or handling of invalid/incomplete pairs. It also equates a one-percentage-point margin with five questions: five out of 470 is approximately 1.064 points. Different interval implementations and that rounding can yield different ship decisions near the threshold.

Before any paid cell runs, freeze the treatment-minus-control direction, confidence level, paired estimator, resampling seed/count if applicable, exact margin of -0.01, and treatment of missing or degraded pairs. Add pure statistical fixtures for all-concordant results, discordant pairs, and values immediately around the boundary. Preserve the invalid-run distinction from F1: incomplete execution is not a favorable quality observation.

For the remaining scope, keep item 2's projection at the serialization boundary: `gbrain/src/core/search/lean-rows.ts:44-65` preserves the full-row escapes, and `gbrain/src/core/ops/search.ts:103-129` places projection after internal consumers. Use actual callability, not merely `surfaceCeiling`, to retain IDs. Also retain LongMemEval's per-question corpus isolation: its current runner resets the database before importing each question's haystack (`gbrain/src/commands/eval-longmemeval.ts:1388-1407`). “One shared index” must mean the same per-question snapshot across arms, not one union of all questions' haystacks. These constraints should be written into the implementation and harness tests rather than inferred by each lane.
