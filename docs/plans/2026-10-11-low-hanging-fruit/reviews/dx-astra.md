### F1 — High: Item 1 changes ordinary search ranking; counting query calls does not waive its quality gate

Item 1's gate says Cat 40 cannot detect the recommendation change because agents rarely call `query` and the token budget never binds. But ordinary `search` passes `expansion: false` without overriding the reranker pool (`src/core/ops/search.ts:756-777`). That pool is 25 in balanced and 50 in tokenmax (`src/core/search/mode.ts:494-510`, `560-581`), and the shared ranking stage takes it from the resolved mode (`src/core/search/hybrid/rank.ts:263-268`). The reranker scores only that head and appends the unscored tail afterward (`src/core/search/rerank.ts:112-116`, `133-143`). A relevant candidate at position 26 can therefore be promoted into the returned results in tokenmax but not by that reranker in balanced, even with the same final hit count and no expansion. This affects the agent's usual search operation, not just the 11 query calls.

The old direct-harness LongMemEval comparison cited in the plan is not a preregistered harm gate for this current operation path. Add a current-tree, single-treatment mode-quality comparison with an explicit harm margin covering ordinary search, including candidates across the 25/50 boundary. Provider spies remain useful for the install receipt but do not establish retrieval quality. Fit this comparison within the existing approved cap using reusable recorded inputs where valid; otherwise defer item 1's default flip. Do not ship it as an unmeasured exception to the plan's opening rule.

### F2 — High: A BEHAVIOR_CHANGES row is not the promised tokenmax-only consent request

Item 1 promises an `ask_user` recommendation once per brain, only for existing tokenmax brains. The proposed table only accepts release-tagged text or a function of chat-fallback disclosure and remote status; it has no mode predicate or per-row action (`src/core/behavior-change-notice.ts:223-226`). Its renderer explicitly says “this is a one-time disclosure, not a request for consent,” emits `kind: 'safety'`, and normally supplies a read-only doctor action (`src/core/behavior-change-notice.ts:466-486`). Delivery is keyed by brain **and channel**, and HTTP additionally by client, rather than the promised single brain-wide recommendation (`src/core/behavior-change-notice.ts:27-48`, `563-576`). An added sentence cannot produce the machine contract an agent needs to stop, ask, and apply the approved change.

Keep the release disclosure separate from a typed, mode-conditional recommendation notice. Specify its consent/action fields, user message, docs link, read-only verification, and durable acknowledgement/dedupe policy. On HTTP, route the configuration change to the brain host's operator instead of instructing an isolated agent to run a local configuration command. Add upgrade tests for tokenmax versus other modes, fresh brains, repeat calls, process restarts, and CLI/stdio/HTTP delivery. Do not change the semantics of every existing behavior disclosure to make this one recommendation work.

### F3 — Medium: Item 1b leaves an agent recovery hint promising expansion that no longer happens

Updating the `expand` parameter description alone leaves a contradictory instruction in actual search results. Concept-shaped searches receive a hint that “the 'query' tool adds multi-query expansion and recovers synonym-phrased matches” (`src/core/ops/search.ts:446-449`); the ordinary search path requests this hint (`src/core/ops/search.ts:792-793`). With item 1b under balanced, the suggested plain query does not expand. An agent following the hint spends another tool round without receiving the advertised recovery behavior. The CLI also advertises query/ask as “RRF + expansion” with only `--no-expand` in the synopsis (`src/cli/top-help.ts:44-45`).

Update these instructions with item 1b, not unconditionally with item 1, since the two gates can produce different shipping decisions. Describe query as mode-dependent and, where expansion is the intended recovery, give the explicit `expand: true` / `--expand` form with the provider/cost caveat. Test the actual emitted hint and help for the shipped default and preserve explicit false as an escape hatch. Do not promise a provider call merely because expansion was requested: the keyless branch returns before expansion and image modality skips it (`src/core/search/hybrid.ts:1133-1140`; `src/core/search/hybrid/arms.ts:229-234`).

### F4 — Medium: The onboarding gate targets the picker event, not the JSON decision the agent relays

The cost matrix has another independently hardcoded copy in the real first-run decision bundle: `SEARCH_MODE_COST` still names Haiku 4.5, Sonnet 4.6, and Opus 4.7, and is embedded in `decisions[].question` (`src/commands/init-first-run.ts:38-49`). The final `init --json` document gets that bundle, not just the picker's `{phase, mode, reason, auto}` event (`src/commands/init.ts:1269-1276`; `src/commands/init-mode-picker.ts:220-227`). The upgrade banner separately recommends tokenmax and repeats the old matrix (`src/commands/upgrade.ts:900-922`). Updating the picker banner and its JSON event can therefore pass the named gate while agents still relay different recommendations and obsolete prices. This is material: the current pricing table lists Haiku 5.5 input at $0.10/M, Sonnet 5.5 at $2/M, and Opus 5.5 at $4/M (`src/core/model-pricing.ts:108`, `117`, `124`).

Name the first-run bundle and post-upgrade banner explicitly in item 1's scope. Derive all matrix copies and ratio claims from the same model/pricing assumptions; update the expansion wording according to whether item 1b actually ships. Assert the final parseable `init --json` document's rendered decision, the non-TTY output, and the applicable upgrade output agree. A picker-unit JSON event is not sufficient evidence for the agent installation experience.

### F5 — Medium: The ID-saving measurement targets starter, while new installations use full

The largest advertised row saving disappears on the normal newly installed surface under item 2's own compatibility rule. New registrations deliberately pin `full` (`src/core/mcp-registration.ts:17-24`), whereas Cat 40's arm uses starter (`gbrain-evals/eval/runner/cat40/gbrain-arm.ts:2-8`; the runner's default is also recorded at `gbrain-evals/eval/runner/cat40-model-ladder.ts:745`). Full leaves fetch callable; starter omits it through its membership sets (`src/mcp/surface.ts:91-110`; `src/core/minions/tools/brain-tool-allowlist.ts:17-44`). Consequently, default full users retain the IDs and receive only the score-formatting part of the saving. A successful starter replay cannot establish a 10–15% reduction for the default installation.

Pin and record both callable and advertised surfaces in the measurement recipe, and label the ID reduction as starter-specific. Add a keyless full-surface payload/token comparison so the report states the benefit new users actually get, separately from the starter benefit. Retain the deep-research compatibility rule; do not narrow registrations to manufacture savings. If the paid run remains starter-only, bound its cost verdict to starter and do not generalize it to full installations.

### F6 — Medium: Item 5 does not specify a machine-visible timing contract or the time being totaled

Adding fields to `onMeta` does not automatically expose them to callers: `buildRetrievalResponseMeta` copies a selected list of hybrid fields (`src/core/ops/search.ts:478-491`), and `--explain` receives that projected metadata (`src/cli/main.ts:1673-1679`). JSON search output takes a different branch that emits the result array, not the explanation header (`src/cli/main.ts:1660-1664`). There is also operation work outside the hybrid callback, including alias fan-out, anchoring, evidence delivery, readiness checks, and saved-fact lookups (`src/core/ops/search.ts:779-794`, `451-470`). The proposed eight stage values are therefore not necessarily an accounting of agent-visible tool latency. Concurrent variant embeddings and vector searches also need wall-time spans rather than a sum of individual request durations (`src/core/search/hybrid/arms.ts:403-406`, `434-467`).

Define stable timing names, units, and boundaries, then explicitly thread the fields into retrieval response metadata and the existing machine-readable diagnostics channel without changing `content[0]` or the CLI array contract. Distinguish hybrid elapsed time from operation elapsed time and account for the residual rather than forcing unmeasured work into a named stage. Cover keyword-only, degraded, empty-result, and retry paths as well as successful hybrid search. The 5% assertion should apply to defined non-overlapping wall-time spans, not to concurrent provider durations. Verify a real MCP response and the chosen CLI machine-readable path, not only the internal perf callback.
