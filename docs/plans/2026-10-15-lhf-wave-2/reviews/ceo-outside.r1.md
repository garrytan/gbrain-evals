### F3 — The $60 smoke is not yet an executable non-inferiority decision

Twenty tasks per model, a −5-point lower bound, and no stated confidence procedure leave the release decision undefined. For a compression change expected to produce mostly ties, even zero observed harm events on 20 independent tasks has a one-sided 95% upper harm-rate bound of 13.9%; zero observed losses alone does not establish the intended claim. Three models on the same 20 tasks are not 60 independent tasks—the existing Cat 40 analyzer explicitly clusters models and arms by task. A bootstrap of all-zero differences can return a misleading zero-width interval. Also, pooled success can conceal a loss on Sol, the model with the remaining cost-per-success gap.

The cost is not demonstrated to fit either. The published Hard M success rates and dollars per success imply roughly $69 for this two-arm, three-model, 20-task design before judges, using the historical task mix (`2026-10-10-model-ladder-hard-confirmation.md:25-29,53-62`). That is a forecast, not a price quote, but it already exceeds $60. Finally, measurement specifies master versus master+item 8 while sequencing says paid gates run on the integrated tree; those are different experiments once items 2 and 9 can change evidence.

Before any paid cell, freeze task IDs and strata, model-level results, confidence level, paired/clustered method and its small-sample behavior, an affordable ledger and exact code/config/corpus pins. Use an integrated-tree ablation with only item 8 different, or the stated isolated pair—not an accidental mix. Test the decision procedure on all-tie and few-regression cases keylessly. Keep the cap: if credible non-inferiority cannot be established within it, report the smoke as descriptive and leave default compatibility-changing behavior off, rather than weakening the rule after seeing results. Require an actual cost-per-success benefit or clearly label a chars-only result; shorter JSON is not itself a dollar-saving verdict.

### F4 — Single-request speed is not the hosted product's latency contract

Item 5 converts serial work into simultaneous pool demand. The delay proxy establishes the benefit of removing awaits for an isolated request, but not what happens when several agents share a small transaction pool. GBrain explicitly supports `GBRAIN_POOL_SIZE=2` to avoid pooler limits (`src/core/db.ts:60-66,226-233`), while the plan fans out response metadata, entity resolution, fusion and post-fusion reads. The same number of queries can now occupy all available connections earlier, shifting the wait to other requests or starving a write. An under-500-ms median at low load could coexist with worse user-visible tails under normal concurrency.

Add a keyless contention gate on the existing delay-proxy/PgBouncer fixture: pool sizes 2 and 6, concurrent searches plus a small write, with before/after p50/p95, timeouts, throughput and queue depth. Freeze a non-regression criterion as well as the isolated-request target. This is validation of the proposed optimization, not a new architecture project. If broad fan-out fails, retain the config-snapshot/settings wins and bound the parallel reads; do not sell borrowed pool capacity as a universal latency reduction.

### F5 — Attendance trigger coverage can improve while the system answers the wrong relationship

“Joined,” “was at” and “went to” are not attendance-only phrases. “Who joined acme-example?” can ask about employment; “who went to example-school?” can ask about education. The current guard does not resolve this ambiguity: `titleSeedTypes` adds meeting/event types only to a fallback title lookup, while an ordinary resolved entity is accepted without that type restriction (`src/core/search/relational-recall.ts:128-157`). Simply adding these phrases to `inVerbs` routes them to `attended`. A negative parser fixture and zero losses on existing attendance templates do not establish precision on those competing intents.

The proposed vocabulary also does not explicitly cover two observed failures in the source audit: “was in the room for” and “took part in.” Freeze the actual failed paraphrases as positives, and resolve broad phrases only when anchor type/context supports attendance; otherwise preserve the normal retrieval path. Add affiliation, education, location and dated-title negatives to the same gate, asserting the chosen relation and returned evidence rather than just whether a parser fired. Define a minimum target-split gain and a false-routing criterion before running the $2 split; “improve” alone can pass by fixing one phrase while creating a new class of wrong answers.

### F6 — Item 10 quietly weakens the study it claims to inherit

The GBRA-94 preregistration does not use only a −1.0-point recall margin. It requires losing at most two of 300 questions, at most two within any question type, nDCG@10 within 0.005, clean-read bounds and an error-rate bound (`2026-10-14-expansion-latency-preregistration.md:134-148`). The plan permits three net losses and drops the other safeguards. On a dataset where the compared arms score 298–299/300, top-10 recall alone is especially insensitive to useful changes in ranking. The old run also pins `rerank-2.5` and cached provider results (`:84-95`); “same 300 questions” does not establish the same experiment at the wave head.

For the two-rewrite change, retain the original acceptance criteria and explicitly pin the comparator prompt/model, reranker and caches, or preregister a justified replacement rule. Report stricter-rank metrics and per-question-type deltas even if aggregate recall passes. Separate evidence for the model substitution from evidence for the prompt substitution. Do not reinterpret an almost-saturated retrieval test as proof about every user who deliberately enables expansion.

### F7 — The claimed expansion-only model change reaches image ingestion unless deliberately isolated

`getImageOcrModel()` falls back directly to `getExpansionModel()` (`src/core/ai/gateway.ts:880-881`). Changing the effective expansion default therefore changes OCR on installs without an explicit OCR model. The cost audit called out this coupling, but the implementation plan promises that only the expansion touchpoint changes without specifying how it will preserve the OCR route. A passing LongMemEval expansion gate says nothing about the text extracted from an image and subsequently stored as memory.

Make unchanged effective OCR routing an explicit acceptance invariant for item 10, with keyless tests for unpinned installs and explicit user overrides. Isolate the measured expansion default from OCR fallback rather than silently extending this wave into an unmeasured ingestion-model migration. No new paid OCR comparison is needed if the stated scope is actually preserved.
