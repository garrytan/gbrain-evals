### F2 — “Zero cosine” and “not hydrated” are different states in the existing rescorer

Item 3 maps zero-norm vectors to NULL/not hydrated and filters dimension mismatches away. That is not enough to preserve the JavaScript behavior. `cosineReScore` returns the original rows unchanged when both hydration maps are empty (`src/core/search/hybrid.ts:1604`). But a decoded zero vector or wrong-dimension vector **does populate the map**; its cosine is zero and every row then goes through the normalized blend (`:1621-1632,1636-1647`).

A keyless probe of the real baseline function with input scores `[1.4, 0.7]` returned those scores unchanged and no cosine fields when all embeddings were missing. With one stored zero vector, or one stored wrong-dimension vector, it returned `[0.7, 0.35]` and `cosine: 0` on both rows. Collapsing those cases can therefore change scores and downstream evidence classifications, even if ordinary vectors agree to 1e-6. A fixture that includes one healthy vector alongside every edge case will conceal the difference because that healthy row keeps the map nonempty.

Preserve hydration presence separately from the numeric cosine: retain a hydrated row with cosine zero for zero-norm and dimension-mismatch cases while avoiding evaluation of an invalid distance operator. Only genuinely absent/non-current/undecodable rows should have the old missing-row status. Preserve the all-empty early return, the mixed text/image behavior and the original error behavior explicitly. Add all-zero and all-dimension-mismatch cases, not just those rows mixed into a healthy batch, to G and the engine parity tests.

### F4 — Detecting missing expression statistics does not make Postgres maintenance repair them

Item 6 promises that existing indexes on both engines regain statistics on the next maintenance pass. The existing F4b maintenance function explicitly returns `skipped: 'not_pglite'` on Postgres (`src/core/planner-stats.ts:242-245`), and its delta tables are PGLite-only (`planner-stats-schema.ts:1-11`). Postgres has a separate first-search guard, but it checks a fixed set of table-column statistics and one projection statistic, not arbitrary expression indexes (`src/core/search/projection-statistics.ts:57-60,155-162,203-206`). Adding an expression-index flag to doctor or a read-side state object does not itself create the promised repair path. With best-effort migration ANALYZE, this matters when the first attempt fails and later succeeds only after the original operation has already been stamped applied.

Name the bounded Postgres repair owner and trigger in the plan, and test an already-present index plus a failed first ANALYZE followed by that actual trigger. Alternatively, state that Postgres recovery is an operator repair, not automatic next-pass recovery. Keep unavailable statistics distinct from absent ones: the existing Postgres guard explicitly avoids treating `pg_stats` hidden by role privileges or RLS as absence (`projection-statistics.ts:140-153`). Apply that distinction to expression indexes too, so restricted roles do not enter repeated ANALYZE attempts or permanent false warnings. The PGLite-only upgrade test presently listed cannot verify the both-engine promise.
