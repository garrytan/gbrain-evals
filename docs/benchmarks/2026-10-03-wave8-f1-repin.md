# The categories after gbrain fix wave 8 and Foundations 1 (2026-10-03)

## The finding

Moving this repository from gbrain `48ed5e8` (v0.60.32.0) to gbrain master `109b992` (v0.60.37.0) changes no category's accuracy, recall or leak count. All 30 offline categories reach the same verdicts at both commits, and all 27 ledger repros still pass. The new checks show each user-facing change these releases make: an unpriced model under a spending cap is refused with steps an agent can follow, `gbrain import` no longer reports success on a directory it skipped, and a time-limited `gbrain embed --stale` now says it stopped early.

The preregistered rules found one regression. It is small: Cat 7's `get_timeline` read at 1,000 pages takes about 0.10 ms instead of 0.05 ms, and the same rule shows 21 other reads within 5% or faster, several far faster. A bisect puts it in Foundations 1's automatic planner statistics. It is logged as [Cat7-1](2026-10-01-wave-bugs.md).

[gbrain](https://github.com/garrytan/gbrain) is a memory system for agents. It stores notes as Markdown and builds a database index for search and relationships. The range holds three gbrain merges:

| Merge | gbrain commit | Release | What it changes |
|---|---|---|---|
| [#5932](https://github.com/garrytan/gbrain/pull/5932) | `566a242a6` | v0.60.35.0 | `search` and `query` append saved facts and follow other names; `derived_from` carries private visibility; PGLite analyzes after imports |
| [#5927](https://github.com/garrytan/gbrain/pull/5927), fix wave 8 | `d82eb2e9e` | v0.60.36.0 | link typing (#5882), pending facts (#5831), Dream reads conversation pages (#4419), `edit_page`, grant fixes, Postgres and Windows fixes, and refusal of unpriced models under a cap the user set |
| [#5962](https://github.com/garrytan/gbrain/pull/5962), Foundations 1 | `109b99217` | v0.60.37.0 | automatic planner statistics on PGLite, creation attribution, seats, unified grants, worktree refresh, ignored-directory import, the embed budget stop |

Measured on 2026-10-03 (UTC) on Bun 1.4.2, with no provider key in any run and System One off. Provider spend was $0. The plan was preregistered in two commits before the runs it governs: the [regression check](2026-10-03-wave8-f1-repin-preregistration.md) and the [new checks](2026-10-03-wave8-f1-coverage-preregistration.md).

## What one of these changes looks like

Say you cap a background job at $0.10 and point it at a model released last week. gbrain has no price for that model, so it cannot know when $0.10 is spent. Before wave 8 the cap was dropped or the model was billed at $0. Now, under a cap you set, gbrain refuses before making any model call. The refusal carries what an agent needs to fix it, as text and as fields:

```json
{
  "code": "no_pricing",
  "model": "litellm:custom-chat",
  "provider": "litellm",
  "kind": "chat",
  "units": ["usd_per_1m_input_tokens", "usd_per_1m_output_tokens"],
  "register_command": "gbrain pricing set litellm:custom-chat --input <usd-per-1M-input-tokens> --output <usd-per-1M-output-tokens> --source <pricing-page-url>",
  "register_scope": "local_cli"
}
```

The text adds: "Over MCP or another remote connection you cannot register prices; ask the brain's operator to run that command." Under the default cap nothing is refused: the job runs and the log names the same command. After `gbrain pricing set`, the retried job is metered at the registered price, and a cap below one call's cost refuses on cost.

The model here, `litellm:custom-chat`, is invented. A small scripted server on 127.0.0.1 plays the provider, so the whole flow costs nothing and returns the same tokens every time.

**The regression: `get_timeline` at 1,000 pages.** The preregistered rule calls a latency change a regression when a read's median (p50) is more than 25% slower and a second paired run on fresh VMs repeats it. Cat 7 measured 0.045 ms at `48ed5e8` and 0.097 ms at `109b992`; the paired repeat measured 0.052 and 0.101 ms. A keyless repro ([`repros/cat7-get-timeline-1k.ts`](2026-10-03-wave8-f1-repin/repros/cat7-get-timeline-1k.ts)) builds Cat 7's 1,000-page brain, runs the reads Cat 7 runs first, then times 2,000 calls:

| gbrain commit | p50 (ms) |
|---|---|
| `48ed5e8` (v0.60.32.0) | 0.034, 0.037 |
| `566a242a6` (#5932) | 0.036, 0.035 |
| `d82eb2e9e` (fix wave 8) | 0.036, 0.038 |
| `109b992` (Foundations 1) | 0.089, 0.096 |
| `109b992` with `GBRAIN_PLANNER_AUTO_ANALYZE=0` | 0.037, 0.037 |

So the change is in Foundations 1, and turning off its automatic planner statistics removes it. After the earlier reads trigger an `ANALYZE` of `pages` and `links`, PGLite plans the unscoped timeline lookup as a nested loop over the `(source_id, slug)` index instead of a hash join; the raw SQL is just as much slower (0.081 against 0.035 ms). About 0.05 ms per call is unlikely to matter to anyone, and the same statistics made other reads far faster:

| Cat 7 read, 10,000 pages | 48ed5e8 p50 | 109b992 p50 |
|---|---|---|
| `search_keyword` | 4.00 ms | 0.13 ms |
| `list_pages_50` | 15.18 ms | 0.91 ms |
| `get_backlinks` | 1.68 ms | 0.53 ms |
| `traverse_paths_d2` | 139.7 ms | 87.0 ms |
| `putPage_single` | 3.83 ms | 0.74 ms |

Bulk `addLink` throughput fell 28% at 1,000 links and 23% at 10,000 in the first run, but only 3% to 10% in the paired repeats, below the rule's 25%. It is reported, not counted. The receipts for all of this are in [`offline-tier/`](2026-10-03-wave8-f1-repin/offline-tier/) and [`cat7-repeat/`](2026-10-03-wave8-f1-repin/cat7-repeat/). The repeat VM at `48ed5e8` ran about 1.5 to 2 times slower on most reads than the first one, so absolute milliseconds differ between VMs; compare a pair, not a column.

**Moves that are not regressions.**

- *N9's relational arm.* It fired on 210 of 435 template one-hop runs instead of 213, and returned 675 candidates in total instead of 735. Hit@1, hit@5, recall@5 and precision@5 are unchanged on all 870 one-hop runs. A bisect with N9 at each merge puts the change in fix wave 8 ([receipts](2026-10-03-wave8-f1-repin/n9-bisect/)), which matches #5882 below.
- *N6's probe count.* Two new operations, `get_write_attribution` and `edit_page`, add access-gate probes; leaks stay at 0, and probes that could detect a leak rose from 421 to 482 per remote caller.
- *Cat 6's diagnostic.* By-mention links to entities the gold does not label fell from 100 to 96; labeled recall and precision stay 1.00.

**Findings about the new behavior.** Neither is a broken contract, so neither is a ledger entry:

- The empty-grant refusal suggests `gbrain auth rescope-token <name> --sources <id,...>` without filling in the token's name.
- `edit_page`'s diff lists the added line before the removed one.

**One observation about search speed.** In D4, each MCP search on the 2,000-note brain took about 200 ms at `109b992` against about 140 ms at `48ed5e8`, in both the development and the counted runs. D4 has no latency rule, so this is an observation, not a preregistered result. gbrain's own fix-wave notes report the same step (about 106 to 140 ms at 10,000 pages) and attribute it to #5932's saved-fact and other-name lookups added to each search. One run at `566a242a6` (#5932 alone), made while other work shared this machine, also measured about 200 ms, which points the same way.

## What to use and what to avoid

- **Set a spending cap and use new models anyway.** Under a cap you set, gbrain stops before spending on a model it cannot price, and tells your agent the one command to run once someone has looked up the price. Without a cap, new models just run. Agents connected over MCP cannot register prices themselves; they will ask you.
- **Import scratch folders inside a repository directly.** `gbrain import ./scratch` now imports it even when the repository ignores it.
- **Treat exit 11 from `gbrain embed --stale` as "partial, resume later".** Scripts that read any non-zero exit as failure need a case for 11.
- **Expect slightly fewer, more accurate typed relationship edges** from prose links, and rerun `gbrain extract links --source db` to apply it to existing pages.
- **The timeline regression needs no action.** If you need the old plan, `gbrain config set planner.auto_analyze false` restores it, at the cost of the much larger gains above.
- **Limits.** All worlds are synthetic, and these worlds were inspected during earlier fix waves; none of this is a held-out result. The sealed confirmation sets were not touched and no corpus was regenerated. Postgres, Windows, pending-write exits, managed `--pull` cycles, worktree refresh, seats and the unified grant columns are not checked here; the [coverage preregistration](2026-10-03-wave8-f1-coverage-preregistration.md) says why for each.
