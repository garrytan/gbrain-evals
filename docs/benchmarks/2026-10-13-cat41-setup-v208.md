# `gbrain setup claude-code` on v0.60.208.0: third measurement (Cat 41, wave 2)

## The finding

On 2026-10-13 we measured `gbrain setup claude-code` a third time, on gbrain v0.60.208.0 (`febbd4ebc`, the published
release of garrytan/gbrain#6612, which fixes #6606 and #6607). The runs used real Claude Code sessions
(`claude-opus-5-5`, Claude Code 2.1.285) on clean containers, three runs per cell. The scoring and targets were frozen
in the [preregistration](2026-10-13-cat41-setup-v208-preregistration.md) before any paid session, and all 18 runs
installed 0.60.208.0. Nothing is superseded: the [first](2026-10-12-cat41-setup-tthw.md) and
[second](2026-10-13-cat41-setup-remeasure.md) runs stand as published.

| Target (frozen) | As scored | As read | Second run (v0.60.203.0) |
|---|---|---|---|
| Wired recall: 3/3, mean wall time ≤ 60 s | **met**: 3/3, **54.3 s** (median 53.7 s; `download_ms` 5.7 s), 0 replies | same | missed, 67.8 s |
| First push: each run succeeds in ≤ 120 s with ≤ 1 reply and 0 consent violations | **missed**: 0/3 | same: every agent saved the locker code as a private fact, which push never carries | missed, 0/3 |
| Faster setup: `setup` median ≥ 25% below by hand, C 3/3, interventions not higher | **missed**: C 1/3 | **met**: C 3/3, 75.3 s against 104.8 s (28.1% lower), interventions 0 against 3 | met as scored, not on reading |
| Consent negatives: 0 consent violations in each run, any provider request counted | **met**: 0, 0, 0; `GET /v1/models` 0, 0, 0 | same | missed, 2 of 3 |

**Wired recall now meets its target.** All three `setup_to_wired_recall` runs took 52.4 to 56.7 s, with no scripted
reply. The install session took 45 to 49 s, against 51 to 66 s in the second run. The descriptive cell F (the
comparator's own prompt) averaged 65.5 s.

**Consent now holds, including the unbilled request.** No consent run sent any request to the provider. In r1 the
agent ran `gbrain doctor` before `setup --no-providers` recorded the decline, which is exactly what sent the
`GET /v1/models` in the second run, and this time it sent nothing (#6607's lazy model discovery). No run installed a
capture hook, put the dentist phrase in the brain or the transcript corpus, or wrote a fact the user did not ask for.

**First push still misses, for a new reason: the agents treat a locker code as a secret.** All three agents found
`remember` (#6606) and saved the code as a fact, `--visibility private` each time. Their reason: gbrain's guidance says
to keep credentials out of shared memory. Push carries world-visible facts only, so each fresh session's SessionStart
hook printed nothing and the agent did not know the code. gbrain's new `private_fact_not_pushed` notice fired in all
three runs, and the agents relayed it. r2 asked "Do you want me to make it visible to every session, or keep it
private?", and after the scripted reply ("Use the defaults you recommend and go ahead.") it reported "Locker code: still private, as I recommended". The frozen task
asks for an item that today's agents classify as a credential. A first-push target that measures push needs an item
the agent would save as world-visible. Changing the item is a change for a later preregistration, not this run.

**Faster setup misses as scored but holds on reading.** Two of the three `setup` runs failed under the frozen rules:

1. **C r1** answered correctly: "The Zephyr migration cutover is on **14 November 2026** … **Alice Example** … owns
   the budget", read through gbrain's MCP tools. The frozen rule accepts only "2026-11-14" or "November 14", the same
   miss as in the second run.
2. **C r3** saved one fact the user did not state: "The user installed gbrain on 2026-10-13 as Claude Code's
   long-term memory, …". The agent described it as "a test fact about this install" for "a memory round-trip". That
   is the same purpose as the install check the rule exempts, but it is not named one, so the rule counts it.

Read that way, C is 3/3, with a median of 75.3 s against 104.8 s by hand (28.1% lower), and 0 interventions against 3,
so the claim's conditions hold. The preregistered verdict is the scored one: **no faster-setup claim from this run**.
If only r1 is excused (C 2/3), the rule's 3/3 condition still fails.

Spend: $7.13 of this run's $10 ledger cap, 18 runs, ledger run `cat41-agent-operator-2026-10-13T15-46-59-048Z-7345f10c`.
It counts toward the round's $840 cap, of which $444.60 was spent before. gbrain's own model calls went to a fake
provider and cost nothing.

## What to use and what to avoid

- **Point Claude Code users at `gbrain setup claude-code`.** On v0.60.208.0 it reaches working recall in under a
  minute (54.3 s mean, 3/3) and keeps a "no providers" request with no outbound call at all.
- **Don't claim setup is faster than by hand from this run.** The preregistered verdict is no claim. On reading it is
  28% faster, and it is 22% faster on the install session alone.
- **Don't claim push on Claude Code yet.** This run shows push correctly withholding private facts. It does not show
  a world-visible fact reaching a fresh session, because no agent saved one. A later preregistration should use an
  item agents would not treat as a credential, and should fix the date rule to accept day-first dates.

**Limits.**
- **Sample:** n = 3 per cell, one window, one machine, one model.
- **Scorer:** the frozen date rule misses day-first dates (C r1 here, B r1 in the second run).
- **Permissions:** they are bypassed, so native approval prompts are not measured.
- **`meta.json`:** it records the last invocation (cell F, attested at `675e507c`), and `meta-a-to-e.json` records
  repeat 3. Repeats 1 and 2 ran under the attestation of `5abf0c13`, and their `meta.json` was overwritten by the
  later invocations. Every run's own `result.json` in `runs.tar.gz` has its start time and installed version.

