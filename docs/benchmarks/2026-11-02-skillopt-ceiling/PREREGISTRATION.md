## Three rules that shape the read

- **A cut needs at most one pair with headroom.** An attempt that fails with two or more headroom pairs, too few to count, is `underpowered`: FIX-METHOD, with the headroom pairs named, and K and L stay undecided.
- **Any cut is scoped to the target the gate measured.** When one target is wholly harness-limited, or Sol's gate is skipped because no Opus pair has headroom and the Opus pairs alone read `saturated`, the verdict covers Opus alone and says why Sol was not measured.
- **Budget refusals are terminal and never scored.** A refusal from the budget ledger, the lease proxy (402, or 503 for a missing key), gbrain's hook cap or the rollout server's cap is never retried and never read as an answer or an error row. The stage it stops reads `incomplete`, which is never a cut.

## Question

Can a harder, substance-scored task set leave room above one Opus 5.5 rewrite of gbrain's shipped `query`, `briefing` and `fact-check` skills, on Opus 5.5 and GPT-6.1 Sol? If it can, does gbrain's SkillOpt loop, as shipped, beat gbrain's one-shot rewrite, and do the outside optimizers beat either? The answer decides K (the optimizer benchmark) and L (gbrain's loop), which #304 left as CUT-CANDIDATEs on hold for this one attempt (R61). Along the way it answers GST-955 (Sol on multi-hop `query`) and gives GST-956 its per-rewrite read of #304's three kept rewrites.

## Evidence class

Calibration reads train only. The gate reads train, selection and the sealed gate split. The 96 test tasks per skill stay sealed until every counted arm is frozen (or until the stop-path read), and are read once.

### 2. Dataset `skillopt-method-v3`

Links are written the way world-v1 writes them (Markdown links to slugs, which gbrain's import turns into its link graph). Pages are 150 to 700 words.
- `query-v3.ts`, `briefing-v3.ts`, `fact-check-v3.ts`: per skill, 24 train, 24 selection, 36 gate and 96 test tasks. Train lists are ordered round-robin by family, so gbrain's batches of 8 each cover every trained family.

### 3. Contract and scorer

- `eval/runner/skillopt-method/contract.ts` appends the skill's contract to every task prompt for every arm (no skill included), except the bare no-skill arm, which gets the task alone (#304's condition).
- Each contract adopts the shipped seed's own documented output shape and adds only what the scorer needs to bind facts, so the seed never fails form for following its own instructions:
  - `query` (the seed asks for a direct response, `[Source: slug, ...]` citations and "the brain doesn't have information on X"): the direct answer first, on an `Answer:` line or as the response's first sentence, holding only the value concluded, with other values and their sources noted after it; "the brain doesn't have information on <name>" or `not in the brain: <name>` for an absent entity; `ambiguous:` naming each candidate for an unresolvable look-alike; each deciding page cited as `[Source: slug]`.
  - `briefing` (the seed lists `- [time] [meeting name]` under MEETINGS TODAY): one entry per external meeting, as the seed's list item or as a heading, starting with that meeting's time and title as the task lists it; inside the entry, the asked fact and `[Source: slug, updated DATE]`, or `No brain page for <name>`.
  - `fact-check` (the seed writes a claim-by-claim report, one `STATUS:` line per `[N] CLAIM:` block, and a Corrections Applied list): the seed's claim-by-claim block, one block for the claim or one per part of a compound claim, each with exactly one `STATUS:` line; the correct value per contradicted part as a `Correct value:` line or the seed's "was X, now Y" correction; deciding pages cited by slug.
- Every v3 check is one m-flag regex over the final text in the task's gbrain rule judge, as in v2, so gbrain's own rule score (the optimizers' reward) and `score.ts` evaluate the same checks; a parity test runs every train and selection task and every seed-template and mutation output through both.
- Substance checks bind facts through loci that do not depend on layout: `query` the first sentence that names any candidate value; `briefing` the meeting's entry, or, when no entry markup is found, text near the meeting's title or an attendee's name; `fact-check` the block or line that names the part. Markup requirements are form checks only. Citations accept `[Source: slug]` and `[Source: slug, ...]`.
- `eval/runner/skillopt-method/score.ts` v3 checks: the answer holds the gold value and no distractor value; each briefing value and citation sits inside its own meeting's entry (the span from that entry's start to the next); every fact-check block's STATUS agrees with the gold for the part or parts it covers, and two blocks for the same part with incompatible statuses fail; look-alike abstentions name every candidate; a value for the wrong date fails because the gold is date-specific. Every check is tagged `form` or `substance`.
- Two scores per task: full pass (every check) and substance pass (substance checks only). Gate bars, K, L, the shipped-skill and rewrite verdicts and GST-955 read substance pass; full pass is reported beside every number.
- Keyless seed-template test: each seed's documented output example, filled with a task's gold values, passes every form check, and its substance checks pass or fail with the values alone.
- Scorer mutation tests: swapped facts between two meetings with every gold token kept; a current value given for a past date; two incompatible `STATUS:` lines for one part; a hedged answer naming the superseded value too; the wrong look-alike; a rescinded amendment's value; a missing per-meeting citation. Each must fail, and paraphrased correct answers in the seed's shape and in the heading shape must pass. Correct content laid out as a table, bold lines or prose passes substance and fails form; entity names never end in an abbreviation that would split the first sentence.

### 4. The headroom gate (preregistered; read before any counted infrastructure is built)

- Split: the gate split, 36 tasks per skill in test's family mix (held-out families included), never shown to any optimizer. It is read by the gate, by its one revision's fresh gate split, and by B0 (section 5), and never after.
- Arms per pair (skill x target), on the gate split, all with the contract:
  - no skill, 1 run per task; seed, 2 runs (run 1 is the designated run for binary comparisons, run 2 is descriptive), and the seed on selection at 2 runs (the bar the one-shot proposals must beat);
  - the shipped-feedback harness one-shot: the seed runs once on each of the 24 train tasks; Opus 5.5 reads the seed, `describeJudges(train)`, and per train task its prompt, tool calls with arguments and returned page names (#304's redaction), final answer and pass or fail; 2 independent proposals, each audited (`audit.ts`) and scored on selection at 2 runs; the kept one-shot is the better on selection, or the seed if neither beats the seed's selection score; only the kept one-shot is scored on the gate, at 2 runs;
  - #304's kept rewrite for the skill (section 6 names them, with their caveats fixed), 1 run: the preliminary GST-956 read;
  - the rubric one-shot (#304's F0b input: `criteria.md` plus failed-check kinds), 1 proposal, 1 run, reported beside the gate and never deciding it;
  - a reachability control on every gate task: the target, told which pages decide the answer (for an abstention task, that no page decides it and which near-miss pages exist), 1 run.
- Calibration before the first gate: train only, at most 3 rounds of the seed at 1 run on Opus, then one read of the frozen knobs on Sol over half the train split, within the approved $50, tuning generator knobs (chain depth, look-alike density, distractor count) toward an Opus seed substance score of 0.30 to 0.60. It never reads selection, gate or test. The frozen knobs and every round's train score go in the preregistration before the gate. Because train holds trained families only, the gate report shows the seed's held-out-family score beside the band.
- Pair labels, every score being substance pass on the whole gate split:
  - `invalid`: the skill's solvability controls fail (target-independent; the skill is invalid on both targets), or on that pair more than 10% of no-skill or seed tasks fail a form check (the contract or its reconciliation with the seed does not work there), or both one-shot proposals fail the audit.
  - `harness-limited`: the target's reachability is below 0.85 on the skill, or more than a third of the kept one-shot's failed tasks end in a 20-turn stop, an output-length stop, or follow a refused decisive read (`tool-calls.ts` classifier).
  - `headroom`: the kept one-shot scores at most 0.80 and at least 0.15 below reachability, and the seed is between 0.20 and 0.70.
  - `saturated`: the kept one-shot scores above 0.80 or within 0.15 of reachability.
  - `difficulty`: room is left but the seed is below 0.20 (too hard) or above 0.70 (too easy for the seed while the one-shot still has room).
  The first matching label in that order applies.
- Scope: when one target is wholly harness-limited, the gate reads the other target's three pairs alone with R = 2, the limited target's own cause is `harness`, and every verdict, a cut included, is scoped to the measured target and says why the other was not measured. Otherwise the gate reads all six pairs with R = 4. Opus pairs run first; Sol pairs that have not run count as U (unknown). Sol's gate is skipped only when no Opus pair has headroom and the Opus pairs read alone (R = 2) are `saturated` (three saturated Opus pairs, for one): no Sol result could make the attempt pass, and the attempt is read on Opus alone and scoped to it. Otherwise Sol's gate runs, and any pair that should have run and did not makes the attempt `incomplete`.
- Pass: no skill invalid on solvability and H >= R. A pass whose pairs cannot reach a 0.10 detectable difference under section 6's repeat rule (three or fewer pairs at the 0.08 floor) is read as `underpowered` and goes to section 8 without B0.
- Cause of a failed attempt, a complete truth table over the scoped pair counts H (headroom), S (saturated), D (difficulty), X (harness-limited), V (invalid) and U (not run):
  - `invalid` when a skill fails its solvability controls;
  - else, when H + D + X + V + U < R (the attempt fails even with every non-saturated pair counted as headroom): `saturated` if H <= 1, otherwise `underpowered` (the ceiling rose on H pairs, too few to count);
  - else `harness` when H + X >= R;
  - else `invalid` when H + X + V >= R;
  - else `difficulty`.
  Only `saturated` can lead to cuts (section 8). Every other cause leaves K and L undecided.
- One revision after a failed attempt, unless the cause is `harness` from gbrain's refusals, which a task revision cannot change (then section 8 runs at once): a dated amendment naming what failed and the knob changes, then regenerated splits (fresh gate and test) and a second gate. A second failure stops the study (section 8).
- `eval/runner/skillopt-method/headroom.ts` stage `gate` reuses F0a and F0b, enforces section 5's per-stage caps, and preflights each target's key (`test -n`); `gateVerdict` returns `pass` (with its scope), `fail` (with its cause, `underpowered` included), `invalid` or `incomplete` (a budget stop), with each pair's label. Keyless tests cover every row of the truth table, including all-difficulty, mixed difficulty and saturation, H = 3 with S = 3, H = 2 with S = 4, Sol wholly harness-limited with Opus (H, S, D) at (1, 2, 0), (0, 3, 0) and (0, 2, 1), two failed reachability gates, and a budget stop. Results are written per pair as they score.
- `eval/runner/skillopt-method/tool-calls.ts` keeps every rollout's tool calls in the receipt (name, arguments, error text) and classifies refusals: multi-selector `get_page`, `known_as_of` beside read-view arguments, a hop chain beside `depth`, other. A recovery is the next call to the same tool succeeding. Stop reasons (turn limit, output length, completed) are counted per arm. Its fixture replays Sol's 651 recorded calls from #304, keyless, through the pinned rollout registry and classifies the refusal text the current pin returns.
- `docs/benchmarks/2026-11-0X-skillopt-ceiling/PREREGISTRATION.md` carries sections 2 to 8's rules and the dataset hashes, with an entry in `docs/benchmarks/preregistrations.d/` so CI's order check covers it, pushed and attested before calibration's first paid call. It states three rules in plain words: a cut needs at most one pair with headroom, and an attempt with two or more headroom pairs that are too few to count is `underpowered`, FIX-METHOD; any cut is scoped to the target the gate measured; and budget refusals are terminal and never scored. Calibration (with the re-priced stages), gate results and any revision are dated amendments.

### 6. The counted comparison (built and run only after a gate pass)

- Pairs: every pair with headroom at the gate that survives B0. A target with no such pair runs only the fixed arms, as a descriptive read, and every K and L verdict is scoped to the target that has counted pairs.
- Splits per skill: 24 train, 24 selection (trained families only), 96 sealed test (48 trained-family, 48 held-out-family), read once after every arm freezes, as one randomized, interleaved batch.
- Arms per pair, all with the contract except the bare no-skill arm:
  - fixed, on test: bare no skill (1 run), no skill (1 run), shipped seed (3 runs; run 1 designated), and #304's kept rewrite for the skill (1 run): `52942b2a` (`query`), `b35934a9` with its `[withheld]` slug rule removed (`briefing`), `a417d566` with the seed's "<5% unverifiable" threshold restored (`fact-check`), on both targets;
  - gbrain one-shot: `runSkillOpt` with `optimizerMode: 'one-shot-rewrite'` (E1, gbrain's default), explicit `tasks`, no `criteriaText` (gbrain's own `describeJudges(train)`), the rollout hook, a fresh skills directory and PGLite engine per run; 3 to 5 repeats (below);
  - gbrain loop: the same with `optimizerMode: 'reflect'` at gbrain's default schedule (4 epochs, batch 8, lr and schedule at their defaults: 12 steps, about 1,032 rollouts), as shipped with the slow/meta update a stub (`orchestrator.ts` 879 to 889), recorded as a known limit; 3 to 5 repeats; its incumbent at 480 rollouts (the last accepted skill when the hook's rollout count passed 480, from gbrain's audit step events) is also frozen and scored;
  - rubric-fed gbrain one-shot (side arm): `criteriaText` set to `criteria.md`; 3 repeats;
  - `best_of_n` at 480 rollouts: 10 harness one-shot proposals under the shipped feedback from one set of train trajectories, each scored on selection at 1 run, the top three rescored at 2 more runs, the best kept if its selection mean beats the seed's by at least 0.05 (gbrain's `VALIDATION_EPSILON`); 2 repeats;
  - GEPA (`optimize_anything`, pinned in a uv lockfile) at 480 rollouts, given `describeJudges(train)` as background and empty feedback on selection; 2 repeats;
  - Microsoft SkillOpt at 480 rollouts with its slow update and meta skill on and its step buffer's selection-score lines removed, only if decision R's spike passes; 2 repeats.
- Every optimizer arm's frozen skill is scored on test at 1 run per task per repeat. A frozen skill that changes frontmatter or the `tools:` list is disqualified on every arm (`audit.ts`).
- Reward, one for every arm: gbrain's rule-judge partial credit as shipped (`scoreTrajectory`), computed by the server from its own task table by task id, since gbrain strips kind tags before the hook sees a task. The counted score stays binary substance pass. A parity test checks the hook, the socket and `scoreTrajectory` agree on every train and selection task.
- Rollout budgets count target rollouts on train and selection. The seed's selection baseline (72 rollouts) is scored once per repeat, served to every arm in that repeat, and counted against each arm's budget. Outside arms have 480 and freeze their best candidate when they reach it. gbrain arms have 1,500, above their full schedule, so the budget never binds them.
- Budget refusals end a run, never score it: inside a gbrain arm the hook throws `SKILLOPT_HOOK_BUDGET_EXHAUSTED`, and gbrain's `aborted`/`budget_exhausted` outcome reads `incomplete` (the repeat resumes after a lease top-up); the lease proxy's 402 (budget) and 503 (missing key), the host ledger's `BudgetExceededError` and the server's own cap are all terminal and never retried; a proxy tripwire 403 invalidates the cell.
- Outcome map, preregistered (implemented with B0's driver; PR 1 pins the outcomes its fake runs produce): `accepted`, `no_improvement` and `errored` with `optimizer_output_unusable` (gbrain's `run-outcome.ts`) are scored results, the arm's frozen skill being gbrain's `finalText` (the seed when nothing was accepted), but only when the run's transport was healthy. Transport health is tracked apart from the outcome: the hook and the ledger record every provider exception, non-2xx response and budget refusal per run, and a run with any of them is an infrastructure error that resumes (below) and is never scored, even when gbrain reports `optimizer_output_unusable`. Only a successful provider reply that gbrain could not use scores as the seed. Fault-injection tests through the real gateway transports cover a provider 5xx, exhausted 529 retries and an unusable 200 reply. Counts per arm go in the receipt.
- gbrain harness settings, preregistered: `maxRuntimeMin` 720 (the 30-minute default would abort the loop), `maxCostUsd` 0 (uncapped in gbrain; the ledger is the cap), `force` true, and `GBRAIN_AUDIT_DIR` set per run inside the receipt directory, so step and slow-update events are kept.
- `eval/runner/skillopt-method/server.ts`: a Bun rollout server on a Unix socket. Run tokens fix arm, skill, repeat, target and budget. It refuses test, gate and out-of-split tasks, returns only scores for selection, reserves each batch's rollouts atomically against the run's budget and returns a terminal budget error at the cap, computes the shared baseline once per repeat (single flight), and meters every call through the ledger. `/lm` serves proposer calls for the Python arms through the same ledger, allows only `claude-opus-5-5`, caps `max_tokens`, calls and tokens per run, and reports proposer calls, tokens and dollars per arm, gbrain's arms included.
- `gbrain-arms.ts`, `best-of-n.ts`, `eval/harness-provider/skillopt_arms/gepa_driver.py` and, if built, `eval/harness-provider/skillopt_arms/ms_skillopt/`. GEPA and Microsoft SkillOpt each run in a Docker container with `--network none`, no keys, a non-root user, a read-only root, memory and pid limits, reaching the harness only through the mounted socket. ### 7. Analysis and verdicts (preregistered with the gate)

- Scores are substance pass. An optimizer arm's score on a pair is the mean over its repeats of the mean over test tasks of its 1-run result. Fixed arms use binary per-task results from one run (the seed's designated run 1; its runs 2 and 3 are descriptive and give the seed's run-to-run spread).
- Intervals: a hierarchical bootstrap (10,000 resamples, fixed seed) that draws connected task groups once per resample and applies the same draw to every arm and target, and draws repeats within arm and pair with an n/(n-1) variance inflation; intervals and two-sided p values use t critical values on (r - 1) x P degrees of freedom (r the smaller repeat count of the two arms, P the counted pairs). A null simulation in the keyless fixture shows false confirmation at or below 5% at 2 and 3 repeats.
- Comparisons, nine in two families, each holding family-wise error at 0.05:
  - L's family, in fixed sequence: the primary, the gbrain loop against gbrain one-shot pooled over counted pairs with equal weight per pair, at 0.05; then, only if the primary is confirmed, the same difference on Opus pairs and on Sol pairs, Holm-adjusted across the two.
  - The outside family, Holm across up to six: GEPA, `best_of_n` and Microsoft SkillOpt (if run) each against gbrain one-shot, and each against the loop at 480 rollouts, pooled.
- A "confirmed benefit" is a point difference of at least 0.05 with the 95% lower bound above 0 at its comparison's level. A comparison's detectable difference is (t at its first-step level + t at 80% power) times its standard error, on the degrees of freedom above: the first-step level is 0.05 for the primary, 0.025 per target and 0.05/6 for the outside family. "Achieved" uses the counted run's own standard error, "projected" the counted amendment's.
- Expected detectable differences at a 0.08 between-repeat spread and a per-task difference variance of 0.10 (0.05 spread in brackets): primary 0.091 (0.065) on six pairs at 3 repeats, 0.099 (0.073) on four at 4 repeats; per target 0.119 (0.090) on three pairs at 5 repeats; outside arms at 2 repeats 0.155 (0.109) on six pairs, so they resolve only large gaps and are reported that way.
- **L, gbrain's loop as shipped** (full default schedule, stub included): KEEP when the primary is a confirmed benefit; the verdict names the targets where the per-target comparison also holds. CUT-CANDIDATE when the primary point difference is below 0.05, its upper bound is below 0.10, its achieved detectable difference is at most 0.10, neither target shows a lower bound above 0 even before adjustment, and test shows headroom (pooled gbrain one-shot at most 0.80). FIX-METHOD otherwise. A tie stays CUT-CANDIDATE for the loop as shipped even when `slow_update` events fire, because the stub is what ships; the report counts epochs that ended in a stub-only slow update and, if the loop stalled there, sends that to GBRA-108 through the Captain as a finding. A 480-rollout loss is reported only as "at that budget". A Sol benefit that coincides mostly with fewer refused decisive reads than gbrain one-shot (`tool-calls.ts`) is labelled "Sol refusal recovery" and sent to GBRA-108 beside the verdict. When only one target has counted pairs, L is read on that target alone and the verdict says so.
- **K, the optimizer benchmark:** KEEP when test shows headroom (pooled gbrain one-shot at most 0.80) and the primary's achieved detectable difference is at most 0.10, or when any comparison is a confirmed difference. KEEP commits the program to v3 and its rollout server as the standing check that every shipped-skill edit (GST-956's rewrites first) and every new optimizer runs against, at about $520 per check (the fixed arms on both targets), with a row added to CLAUDE.md's "Match a change to a useful test" table; the full optimizer comparison is not rerun without a new question. CUT-CANDIDATE when test saturates (pooled gbrain one-shot at least 0.90). FIX-METHOD otherwise. Scoped like L when one target has no counted pairs.
- **Outside arms:** a confirmed benefit of GEPA, `best_of_n` or Microsoft SkillOpt over the loop at 480 rollouts gives the loop an added FIX-METHOD naming that mechanism.
- **Rubric side arm:** reported against the shipped-feedback one-shot and the loop, as what writing criteria text buys a user.
- **Shipped skills,** per pair, on binary substance results with #304's rule (KEEP when the bootstrap lower bound is above 0 and the exact McNemar p is below 0.05; CUT-CANDIDATE when the point difference is 0 or below; else FIX-METHOD): the verdict read is the seed against no skill with the contract, which asks whether the skill's guidance adds substance beyond its output format. The seed against bare no skill on full pass is reported beside it as value to users with format included.
- **#304's rewrites (GST-956, the gate for shipping them):** a separate result per pair for each rewrite against its shipped seed, on substance, by #304's rule: `rewrite-beats-seed`, `rewrite-worse` or `no-difference-shown`, on Opus 5.5 first and on Sol once Sol runs. The gate report carries the preliminary read on the 36 gate tasks; the deciding read is on the 96 test tasks (the counted run or the stop-path read).
- **GST-955:** on Sol `query`, the seed against bare no skill and against no skill with the contract on the multi-hop test tasks (two-hop and three-hop), with Sol's refusals by class and its recovery rate, read by the shipped-skill rule.
- A keyless fixture with mixed per-task success runs through the estimator, the bootstrap, McNemar and every verdict function.
- Every null or negative gets R48's "Why null?" (exposure, task fit, power and saturation, frontier model).

### 8. Stop path (the gate fails twice, fails once with a cause no revision can change, or passes on too few pairs to power B2)
