# Relationship extraction after the move to gbrain master

**Measured September 29, 2026.** This repository now installs gbrain master [`b80cad6`](https://github.com/garrytan/gbrain/tree/b80cad61e4725e62531439c027053387c98e23f8) (v0.59.13.0) instead of `939232f` (v0.55.0.0), a commit that exists only on a side branch. Three keyless categories were re-run at both commits on the same scorers: relationship-aware search (Cat 1), link type accuracy (Cat 2) and link extraction under tricky prose (Cat 6).

**The finding.** Moving to master changed none of the three results. Cat 1 and Cat 6 are identical at both commits. Cat 2's published 86.6% type accuracy, however, depended on a scorer defect: the answer key stored attendance edges pointing from the meeting to the person, the opposite of how gbrain stores them. With the direction corrected, both commits score **74.7% type accuracy (109 of 146 found pairs)** and **18.8% strict F1**. The 86.6% figure is withdrawn as a current measurement; it stays in the April report with a note.

## What these categories check

gbrain turns Markdown notes into a searchable database. When a note about a meeting links to a person, gbrain can record a typed relationship ("this person attended this meeting") instead of a bare mention. The world-v1 corpus is 240 fictional pages (people, companies, meetings, concepts) whose generator also recorded the true relationships, so extraction can be scored against a known answer.

- **Cat 1** (`eval/runner/before-after.ts`) asks 145 "who works at / invested in / advises / attended X?" questions and checks whether ranking typed relationships first puts correct people in the top five results.
- **Cat 2** (`eval/runner/type-accuracy.ts`) runs gbrain's link extractor on every page and compares each typed edge with the answer key. Type accuracy is correct / (correct + mistyped) over the gold edges the extractor found. Strict F1 combines precision over every inferred typed pair with recall over all 280 gold edges.
- **Cat 6** (`eval/runner/cat6-prose-scale.ts`) plants 250 traps in page prose (links inside code fences, slugs that are substrings of other slugs, ambiguous roles) and checks that the extractor links what it should and nothing else.

These are regression checks on generator-written data. They show whether extraction changed, not how well it works on real notes.

## Results

### Cat 1: relationship-aware search

| Metric (145 questions) | Text only | Relationships first |
|---|---|---|
| Precision@5, 5 slots per question (725) | 29.9% (217/725) | 35.4% (257/725) |
| Recall@5, 261 required answers | 83.1% (217/261) | 98.5% (257/261) |

Identical at `939232f` and `b80cad6`, with the same counts (217 and 257 correct) as the September 28 re-run quoted in the April erratum. The gate (relationships first never worse than text only) passes at both.

### Cat 2: link type accuracy

| Scorer and commit | Type accuracy (correct / found) | Strict F1 | Attendance edges typed correctly (of 134) |
|---|---|---|---|
| September 28 scorer, `939232f` | 86.6% (240/277) | 41.3% | 131 |
| Corrected scorer, `939232f` | 74.7% (109/146) | 18.8% | 0 |
| Corrected scorer, `b80cad6` | 74.7% (109/146) | 18.8% | 0 |

The other four relationship types score the same in every row: invested in 55/75, founded 32/40, advises 12/17, works at 10/10.

Why attendance moved. gbrain stores attendance as person → meeting, both for a meeting's `attendees:` frontmatter and for body links it treats as attendance (`orientCanonicalAttendance` in `src/core/link-extraction.ts`). The answer key used meeting → person, and the scorer read every candidate as coming from the page being scored. At `939232f`, the extractor typed every person linked from a meeting page as `attended`, pointing the wrong way, and those reversed edges matched the reversed key: 131 "correct" edges. Scored in gbrain's own orientation, those 150 reversed edges are spurious and all 134 real attendance edges are missed.

At `b80cad6`, the extractor types a body link as attendance only when it appears in an attendance list, such as an "Attendees:" line (added in gbrain v0.58.0.0). The world-v1 meeting pages describe attendees in prose (one attendee "dialed in from Singapore") and have no such list, so master records those links as plain mentions. The table therefore shows the same numbers for different reasons: the old extractor produced reversed attendance edges, the new one produces none. Neither recovers attendance from this prose.

The regression floors in `type-accuracy.ts` moved from 80% / 35% to 70% / 15%, below the corrected measurement. They were set on September 28 below the value the defective scorer produced.

### Cat 6: extraction under tricky prose

All 250 traps are handled at both commits: link precision, recall and F1 of 1.0, no code-fence or inline-code leaks, no substring false positives, and every ambiguous role typed as labeled. Precision is measured on labeled injections only.

## What to use and what to avoid

- The re-pin is safe for these categories: no extraction or ranking change on world-v1.
- Do not cite 86.6% type accuracy. The current figure is 74.7% (109/146) with 18.8% strict F1.
- Attendance written as prose is not recovered as a typed relationship at either commit. If your meeting notes list attendees on an "Attendees:" line, current gbrain can record them. We have not measured that case.
- The keyless relational retrieval smoke (`bun eval/runner/relational-ab.ts --stub-embed --seeds 1`) still shows relationship retrieval firing on 0 of 50 "who attended" questions at `b80cad6`. That run uses hash embeddings, so only the firing count means anything. It is recorded here as an open problem, not a measurement.

## Reproduce and inspect

No API keys, no network, about 20 seconds in total:

```sh
bun install --frozen-lockfile
bun eval/runner/before-after.ts
bun eval/runner/type-accuracy.ts                        # b80cad6
bun eval/runner/type-accuracy.ts --package=gbrain-cues  # same scorer on 939232f
bun eval/runner/cat6-prose-scale.ts
```

The old-scorer rows come from a clean checkout of gbrain-evals `c9e90ad` (v0.10.2), which installs `939232f`.

Raw receipts are in [2026-09-29-repin-cats-1-2-6/](2026-09-29-repin-cats-1-2-6/):

- `*.b80cad6.receipt.json` and `type-accuracy.939232f-corrected-scorer.receipt.json` are schema v2 receipts from gbrain-evals commit `c3ec550` with a clean tree. They record the executed source-tree hash and the loaded package's content hash: `740db8d8…` for `b80cad6` and `74974a32…` for `939232f` (installed as the `gbrain-cues` alias).
- `*.939232f-v0.10.2-runner.receipt.json` are schema v1 receipts from `c9e90ad`.
