# The low-hanging-fruit wave's paid gates: `query` expansion follows the mode ships, `balanced` as the new-install default does not (2026-10-12)

## The finding

[gbrain](https://github.com/garrytan/gbrain) is a memory system for agents. This file reports the paid gates of the
low-hanging-fruit plan (gbrain-evals `docs/plans/2026-10-11-low-hanging-fruit/PLAN.md`, #134), run under the rule
committed before any counted call ([preregistration](2026-10-12-lhf-wave-preregistration.md)). Items 0 and 2 to 5 are
keyless and are gated by gbrain's own tests, so they are not measured here.

**Item 1b ships: `query` no longer expands on `balanced`.** Without expansion, `balanced` answered 451 of 470
LongMemEval-S questions in strict `recall_all@5`. With expansion it answered 448. That is +5/−2, an estimate of
+0.64 points and a one-sided 95% lower bound of −0.21 points (the gate needs more than −1.0). Operation latency p50
fell from 2,216 ms to 370 ms, and each query makes one embedding call instead of three plus one expansion call.

**Item 1's default flip does not ship.** On LongMemEval-S, `balanced` tied `tokenmax` exactly in both comparisons,
451 vs 451 with no question disagreeing, so both passed. The second gate, the Cat 40 Hard world M rerank-pool replay,
was **inconclusive**: over 966 paired calls, gold hit@5 under a 25-row rerank pool was 37.0% against 37.9% under 50.
That is −0.93 points with a lower bound of −1.55. The flip needed every gate to pass, so it was reverted on gbrain
`capy/lhf-wave` (`a5044b1d0`). Inconclusive is not harm: the estimate is inside the margin, but 966 calls cannot rule
out a loss of more than a point. New installs with a chat key are still recommended `tokenmax`. The rest of item 1
ships: the Voyage-key branch of the init picker, reading keys from config files, `gbrain init --search-mode` and the
doc corrections.

Tested configuration: gbrain `f77f1418caedc2f521e30ba14040134d09310a49` (tree `585e2fbf12a5`). That is master
`52adb3d95` (v0.60.180.0) plus the wave's items 1, 1b, 2, 3 and 4, the via-operation harness fixes and the #6495
timeout-reason fix. The shipped pull request differs only by the dropped flip, master merges and release stamps.

### Cat 40 Hard world M rerank-pool replay

The 1,030 recorded hybrid `search` calls of the 2026-10-10 Hard confirmation's `gbrain-hard` cells were replayed on a
freshly built world M brain through `gbrain serve --surface starter`. Both arms pinned `search.mode` to `tokenmax` and
differed only in `search.reranker.top_n_in` (50 vs 25). The procedure is
[`cat40-hard/RERANK_POOL_REPLAY.md`](cat40-hard/RERANK_POOL_REPLAY.md).

| Arm | Calls | OK | Gold calls | Gold hit@5 | Rerank tokens |
|---|---|---|---|---|---|
| pool 50 | 1,030 | 1,030 | 966 | 37.9% | 4,786,415 |
| pool 25 | 1,030 | 1,030 | 966 | 37.0% | 2,609,230 |

The difference is −0.93 points with a one-sided 95% lower bound of −1.55 points. The rule passes above −1.0, fails
when the estimate is below −1.0 and is inconclusive otherwise, so the verdict is **inconclusive**. By family, the
25 pool lost 2.4 points on H2, 0.9 on H3 and 0.8 on H4 and gained 0.8 on H1. H5 tasks name no gold documents. The 25
pool was the first 25 rows of the 50 pool on every call. The pool matters for what the agent sees even when gold hit@5
barely moves: mean top-20 overlap between the arms was 0.772, and fused rows 26 to 50 reached the top 20 on 933 of
1,030 calls (90.6%).

Receipts: [`receipts/cat40-rerank-pool-replay/`](2026-10-12-lhf-wave/receipts/cat40-rerank-pool-replay/), containing
`summary.md`, `summary.json`, the run receipt, `calls.ndjson.gz` (both arms' top rows for every call),
`chunk-index.ndjson.gz` and the slot build receipt with its coverage file.

## Validity notes

- **One invalid run, rerun once.** The first Q-B-on run recorded one `rerank_failed` provider error (question
  `c19f7a0b`), which makes the arm invalid under the rule. It was rerun once unchanged. Only the clean rerun enters
  C3. The invalid run is kept in [`receipts/Q-B-on.invalid-run1/`](2026-10-12-lhf-wave/receipts/Q-B-on.invalid-run1/).
- **The Cat 40 slot needed a drain.** The world M build regenerated byte-identical to the confirmation's world
  (`world.json` SHA-256 `99c53db0…`), but the slot build stopped at `HARD_SLOT_EFFECTS_QUEUED`: 37,391 persistence
  effects were still queued even though all 78,487 chunks already had embeddings. A one-off script with every provider
  key disabled drained them, and the slot was snapshotted again (`slot0.coverage.json` records `queued_effects: 0` and
  who drained it). No provider request was made during the drain, and no replay call ran before it. gbrain-evals
  v0.10.79 (#137) fixes the cause in the slot builder: the warm boot now holds the server until gbrain reports no
  drain in progress.
- **What `tokenmax`'s synopsis vectors add is not measured.** Under the amendment "one index for every arm", the
  `tokenmax` arms read the shared title-tier index, because building per-chunk synopses for about 100,000 chunks was
  outside every cap. C1 and C2 measure what `balanced` changes at query time (pool, limit, budget), which is what a new
  install's default would change.
- **Cat 40 calls are treated as independent.** The bootstrap resamples calls, not cells, as the amendment states.

## Item 5: per-stage search timings (no paid run)

gbrain v0.60.205.0 (gbrain#6601, master `22d407d82`) adds `_meta.retrieval.timings` to every `search` and `query`
response and a `timings:` line to `--explain`. It is instrumentation, so the gate was that results stay identical and
the stages account for the time. Both were checked on the keyless refactor-wave-1 bench (400 pages, PGLite,
deterministic stub embedder and reranker, 20 queries through `search` and `query`, 40 responses):

- **Results unchanged:** all 40 per-response result digests on `22d407d82` match master just before the merge
  (`148b74d14`, v0.60.204.0, run with the same bench script in `--results-only` mode); combined digest
  `7727530313ca5883` on both.
- **Time accounted for:** `other_ms` (time no stage claimed) was 0 ms on all 40 responses, against the bench's 10%
  limit. Response totals: median 46 ms, p95 52 ms, max 55 ms. Summed over the 40 responses, `fuse` (688 ms),
  `vector` (374 ms), `lexical` (286 ms) and `post_fusion` (210 ms) take most of the time.
- **Before the merge:** the PR measured `other_ms` at or below 1.6% of every response's total on PGLite and Postgres;
  the PR's full Ubicloud gate was green on its final tree.

The bench uses stub providers, so these timings show where gbrain's own time goes, not provider latency. No paid
sample was run for item 5. Receipts: [`receipts/item5-timings/`](2026-10-12-lhf-wave/receipts/item5-timings/).
