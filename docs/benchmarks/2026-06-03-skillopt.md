# Can a skill teach itself to be better? — SkillOpt benchmark

**Date:** 2026-06-03 · **gbrain:** v0.42.9.0 · **Corpus:** `skillopt-v1` (fully fictional)

## The one-paragraph version

gbrain ships a feature called `skillopt` that lets an agent's *skill* — the
markdown instructions that tell it how to do a job — rewrite itself to get
better at that job. The obvious worry with anything self-improving is that it
learns to game its own test instead of actually improving. So we built four
experiments that try to break it: does it really get better, does it cheat, do
the gains survive being moved to a different model, and is the self-rewriting
loop even worth the cost. Here is what we found, with the numbers and the way to
reproduce them.

## How the test works (plain English)

We start with four deliberately **bad** skills, each with one clear flaw:

| Skill | The flaw |
|---|---|
| brief-writer | never includes a risks section or a confidence level |
| thorough-analyst | rambles; no length discipline |
| quick-answerer | answers from memory; never checks the brain |
| advisor | discusses endlessly; never commits to a recommendation |

Each skill comes with two sets of tasks that share no items: a **training set**
the optimizer is allowed to learn from, and a **held-out set** it never sees
during optimization. We score the skill on the held-out set *before* and *after*
optimization. Improvement on a set it never trained against is the only thing
that counts — that is what tells you the skill genuinely got better rather than
memorizing its homework. We compute those held-out scores ourselves; we do not
trust the optimizer's own report of how it did.

The target agent runs on Claude Haiku 4.5; the optimizer that proposes rewrites
runs on Claude Sonnet 4.6. Every number below is reproducible from this commit.

## Result 1 — skills measurably improve (cat30)

Every one of the four deficient skills went from **failing to perfect** on its
held-out set:

| Skill | Held-out before | Held-out after |
|---|---|---|
| brief-writer (missing structure) | 0.00 | **1.00** |
| thorough-analyst (too verbose) | 0.00 | **1.00** |
| quick-answerer (no brain-first) | 0.00 | **1.00** |
| advisor (no verdict) | 0.00 | **1.00** |

**4 of 4 improved. Gate: PASS.** ($4.95)

The skills fixed themselves on tasks they were never optimized against. That is
the whole claim, and it holds across all four flaws.

## Result 2 — it can't cheat its way there (cat32)

This is the experiment that matters most for trust. We gave the optimizer a
benchmark whose scorer is *gameable*: it checks for the presence of section
headers, which a skill can satisfy by emitting empty headers with nothing under
them. Then we measured real quality with a separate, independent LLM judge that
the empty-header trick can't fool.

- **The cheat is real and the independent judge catches it.** A hand-built
  cheating skill scores **1.00** on the gameable check but only **0.28** on the
  real-quality judge — a 0.72 gap. The gameable scorer is fooled; the held-out
  judge is not.
- **The optimizer, run against only the gameable scorer but with the held-out
  check switched on, did not regress real quality** — held-out quality actually
  rose from **0.22 to 0.48** while the gameable score maxed out. The independent
  check is what stands between "looks good" and "is good."

**Gate: PASS.** ($1.63)

## Result 3 — the gains move to other models (cat33)

A skill is just instructions, so a good rewrite should help no matter which model
runs it. We optimized on one model and then scored the result on a *different*
model with no further optimization.

| Optimized on | Evaluated on | Unoptimized | After transfer | Native ceiling |
|---|---|---|---|---|
| Haiku | Sonnet | 0.00 | **1.00** | 1.00 |
| Sonnet | Haiku | 0.00 | **0.71** | 0.96 |

**2 of 2 transferred. Gate: PASS.** ($9.22) Optimizing on Haiku produced a skill
that scored perfectly on Sonnet untouched. The reverse direction kept about 74%
of the benefit a model would get from optimizing on itself. The improvement is
in the instructions, not a quirk of one model.

## Result 4 — is the self-rewriting loop worth it? (cat31)

We ran the same seed four ways and scored each on the held-out set, against a
floor of doing nothing:

| Variant | Held-out | Training-set | Cost |
|---|---|---|---|
| no optimization (floor) | 0.00 | — | — |
| **A — full loop + validation gate** | **1.00** | 1.00 | $0.98 |
| B — single-reflect loop | 0.92 | 1.00 | $0.94 |
| C — one-shot rewrite (no loop, no gate) | 1.00 | 1.00 | $0.88 |
| D — greedy, no validation gate | 0.92 | 0.80 | $0.96 |

**Gate: PASS** on the two claims this can honestly prove:

- **The optimizer works:** every variant lifts the skill from 0.00 to ~1.00 on
  the held-out set.
- **The validation gate is free insurance:** the gated pipeline (A, 1.00) is at
  least as good as the greedy no-gate variant (D, 0.92) on held-out — turning the
  gate on never costs quality. Its real payoff, refusing edits that game the
  score, is the cat32 result above.

And the honest part: on a simple, clearly-specified flaw, a **one-shot rewrite
(C) ties the full loop** — both reach 1.00. We do not claim the loop beats a
one-shot rewrite here, because it doesn't; the seed is too easy to separate them.
The loop's advantage is the safety gate and, we expect, harder multi-part skills
a single rewrite can't fully fix. We would rather report the tie than dress it up.

## What we are NOT claiming

- These are small, single-flaw skills chosen so each result is unambiguous. They
  show the mechanism works and is safe; they are not a stand-in for optimizing a
  large production skill, which we expect to be messier and partial.
- On a simple, clearly-specified flaw, a one-shot rewrite does about as well as
  the full loop (see cat31). The loop's distinct value is the safety check that
  blocks cheating (cat32) and, we expect, harder multi-part skills.

## Reproduce

```sh
cd ~/git/gbrain-evals
bun eval/runner/cat30-skillopt-improvement.ts        # improvement (4 seeds)
bun eval/runner/cat32-skillopt-reward-hacking.ts     # cheating defense
bun eval/runner/cat33-skillopt-transfer.ts           # cross-model transfer
bun eval/runner/cat31-skillopt-ablation.ts           # is the loop worth it
```

Each writes a receipt under `eval/reports/` — which is **gitignored**, and,
unlike the PrecisionMemBench report (whose backing JSONs are committed under
`docs/benchmarks/2026-05-29-precisionmembench/`), the receipts behind THIS
report's numbers were never hand-copied into `docs/benchmarks/2026-06-03-skillopt/`
before they were cleaned up. That is a provenance gap, disclosed rather than
papered over: the runs call live Haiku 4.5 / Sonnet 4.6, so a re-run reproduces
the gate outcomes but not the exact cost figures or byte-identical scores.
Anyone re-running should copy the four `receipt.json` files (cat30/31/32/33)
from `eval/reports/` into `docs/benchmarks/2026-06-03-skillopt/` so the next
version of this table has committed artifacts.

Also note: the held-out task sets were regenerated on 2026-08-31 with
differentiated judge criteria (stricter, differently-phrased checks the
optimizer never sees — audit finding skillopt-cats-09; see
`eval/generators/skillopt-v1-gen.ts`). The numbers above predate that change
and were measured when held-out and training tasks shared byte-identical rule
checks, so "held-out" in this report demonstrates topic transfer only; future
runs hold the judge criteria out too.

The deficient skills + task sets are
in `eval/data/skillopt-v1/`, generated deterministically by
`eval/generators/skillopt-v1-gen.ts`. Scores are computed by the harness, not
read from the optimizer's own bookkeeping.

## A note on getting here

The first full run of this suite scored **0/4** on improvement, and it taught us
more than a clean pass would have. Running the feature against live models
surfaced five real bugs that unit tests had missed — a tool-loop incompatibility
with a new SDK, a pricing-table gap that silently zeroed every cost-capped run,
a swallowed error, and most importantly: the optimizer was never told *what the
scorer rewards*, so it kept proposing reasonable-but-wrong edits that never
passed. Once it could see the success criteria (while the independent held-out
check kept it honest), the four skills went from 0.00 to 1.00. Each fix is in
gbrain v0.42.9.0. That is the point of running evals against real models: the
bugs that matter only show up when the whole thing actually runs.
