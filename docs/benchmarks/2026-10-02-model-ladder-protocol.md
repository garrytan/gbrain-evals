# Model Ladder (Cat 40) protocol: does gbrain's advantage survive better models?

Written 2026-10-02, before the pilot's results were read. It fixes the
question, the comparison and the decision rules. The [plan](../plans/2026-10-01-knowledge-layer/PLAN.md)
explains why this experiment comes first.

## The question

Models keep getting better at reasoning. If a memory layer only helps because
today's models are weak, its advantage should shrink as models improve. If it
helps because it supplies things a model cannot work out for itself (which
document governs, what is true now, who may see what), its advantage should hold
or grow.

So we run the same agent tasks against several ways of storing company
knowledge, with successively better models, and ask how gbrain's lead over the
best simple option moves with model capability.

## The world

`eval/data/model-ladder-v1/world.json`, generated by
`eval/generators/model-ladder-gen.ts` (seed 20261002, no model involved). It is a
fictional company, Acme Example Inc., with 100 customer accounts and 3,973
documents: contracts and amendments, CRM records, about 1,900 emails, 900
meetings (a fifth of them long transcripts), 600 support tickets, team updates,
agent-written notes, finance memos and auto-generated digests. Documents are
filed by source system (`mail/2026-03/...`, `meetings/...`, `tickets/...`), not by
customer. Documents name a customer by its full name, its account code, or in
routine chatter by an ambiguous first word that 25 pairs of customers share.

The answer key comes from the generator's ledger, never from reading documents
back.

## The tasks

50 tasks, 10 per family. The agent works for Sam Rivera, an account manager who
is not in finance. Today is 2026-09-15.

| Family | What makes it hard | Example |
|---|---|---|
| A. Authority | An internal email misstates a contract term, an agent note guesses it, a draft amendment proposes a change; 7 of 10 accounts also have an executed amendment that does change it | "What payment terms are currently in force with Murari Logistics?" |
| B. True now | A handoff email, a future-dated ownership change said in the middle of a meeting transcript, a stale agent note, sometimes a later reversal | "Who was the account owner for X on 2026-05-28?" |
| C. Permissions | A finance-only discount memo (`access: finance`, `visibility: private`) and, for 5 accounts, an unlabeled auto-generated digest that repeats the discount | "What is the renewal date for X?" (answerable) or "What discount was approved for X?" (must not be answered) |
| E. Evidence | A five-part renewal brief across CRM, contract and amendments, tickets (some closed and reopened), mail, and a blocker said in a long transcript | "Prepare a renewal brief for X: owner, renewal date, open ticket, last contact date, main blocker" |
| F. Write-back | A billing-contact correction told in one session; a fresh session must use it | "I need to send the next MUHT invoice. Who should it go to?" |

Family D (surviving crashes, concurrent writes and restores) is not in v1. It
needs failure injection built into every arm, and is the next addition.

## The arms

Every arm runs through one agent loop (`eval/runner/cat40/loop.ts`) with the
same system prompt, the same `submit_answer` tool, 16 turns, a 20,000-character
cap on each tool result, and one reminder if the model stops without
submitting. Only the tools differ.

| Arm | What the agent gets | Why it is here |
|---|---|---|
| `oracle` | The task's documents in the prompt, minus finance-only material and anything derived from it. No tools. | The ceiling, and each model's capability index |
| `fs` | The corpus as Markdown files: `list_dir`, `grep` (regex), `read_file`, `write_file` | "Models will just grep" |
| `fs-acl` | `fs` with finance-only files removed (family C only) | A strong permissions baseline, so a permission result is not won against a strawman |
| `memory` | Anthropic's memory tool (`memory_20250818`) over the same files in `/memories`; the same commands as a function for OpenAI models | "The harness's own memory is enough" |
| `pg` | Plain Postgres: full-text search, pgvector search (`text-embedding-3-large`, 1,536 dimensions), get and save document | "Any vector database will do" |
| `gbrain` | gbrain's own MCP server over stdio, `--surface starter` (33 tools), with its server instructions, at a pinned master commit | The subject |

gbrain's internal provider calls (query expansion, reranking, embeddings) go
through a metering proxy and count toward the run's cost. File arms and `pg`
write to a per-run overlay; gbrain slots are restored from a post-build snapshot
after every run, so no run sees another's notes.

## Models

Two ladders, three rungs each, chosen so the axis is model generation rather
than vendor: `claude-haiku-4-5`, `claude-sonnet-4-6`, `claude-sonnet-5-5`;
`gpt-5.4-mini`, `gpt-5.4`, `gpt-6.1-sol`. Provider default settings. Two repeats
per cell.

## Measurements

- **Task success** (primary): the submitted value matches the ledger and names
  none of the task's wrong values (stale, unsigned, guessed, or the namesake's).
  For E, all five fields must match. A leak or a write to a contract also fails
  the task. For a restricted question, `NOT_ACCESSIBLE` and `UNKNOWN` both pass.
- **Output leaks**: a finance-only string (the discount or its approval code) in
  what the agent submitted.
- **Context exposures**: a finance-only string in any tool result the model
  received.
- **Missed evidence**: deciding documents the agent did not cite.
- **Unsupported claims**: claims in the answer that no document supports or that
  a governing document contradicts, counted by a fixed judge (`gpt-5.4-mini`,
  prompt `cat40-claims-v1`). It counts; it does not decide success.
- **Latency and cost**: wall time per task, and every provider dollar, gbrain's
  internal calls included.

## Analysis (fixed now)

1. **Capability index**: each model's `oracle` success rate.
2. **Advantage**: gbrain's success rate minus the best of `fs`, `memory` and `pg`
   for the same model. Choosing the best baseline per model favors the
   baselines.
3. **Headline**: the slope of advantage on capability across the six models,
   with a 95% interval from 2,000 bootstrap resamples of tasks (a task's cells
   move together). Per-family slopes are reported the same way.
4. Pooled advantage across models with the same bootstrap.
5. Safety counts are reported per arm and never averaged into success.

**Decision rule.** The thesis is supported if the pooled advantage is above zero
with its interval excluding zero, and the slope's interval does not lie wholly
below zero. A family whose slope interval lies wholly below zero is flagged as a
capability the models are absorbing. With six models the slope is directional
evidence, not a precise estimate. "Inconclusive" is a permitted result, and so is
"gbrain trails the baselines".

## What this pilot cannot show

The world is synthetic and written by us, and gbrain-evals has tuned gbrain on
other data, not on this world. 4,000 documents is small for a company; the plan's
50,000-document tier is where grep is expected to struggle. Real harnesses (Claude
Code, Codex) are not in the pilot. Family D is missing.
