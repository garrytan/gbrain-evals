- **Weekly held-out line: a pilot and a judge check on public dev worlds, built by the weekly generator.** The pilot runs the line's four rows (gbrain at 8,000 tokens, the extract-first server, the memory-bank server and the 40-turn grep agent) on public dev world bg1-dev-01 with the counted readers, judges, effort and limits; only the set, the loader, the worlds and each cell's lease differ from a counted week's cells. Each row's pilot is capped at a tenth of its block budget, split between the row's cell and particle-1's re-read, each with its own ledger. The judge check runs the grep agent on bg1-dev-02 and bg1-dev-03, so each gating judge has enough answers to be checked against. `bun eval/runner/weekly-line/pilot.ts plan` is the dry run. It prints every cell, ledger and cap, the judge check's pause and the Claude Code quick look (reported as skipped, since it needs a new runner), and calls nothing. `pilot.ts campaigns` writes one campaign per ledger, only for a granted paid window that covers every cap, and `pilot.ts report` reads back whether each row's part under test ran, every answer's verdict, each row's cost from the provider usage fields, the ceiling and a week projected at the measured rates. `bun eval/runner/weekly-line/judge-check.ts` draws each judge's sample of at least 100 answers, at least 40% judged wrong, stratified by verdict and by whether the agent answered without a tool call, hedged or neither; labels each from the question's gold, stale and decoy values where they settle it and from gemini-3.8-flash otherwise (with a dry-run mode that sends nothing); and reports each judge's kappa with the source of every label. The paid-window guard in front of `cell.ts run`, the campaign launch check and the re-read's gating-judge rule now cover these cells, and the grep agent's answers record each tool's calls and failures. Keyless tests in `test/eval/weekly-line-pilot.test.ts` cover each change.
